## Goal

Every lead lives in NexaGen, Frappe shows the same pipeline, and Meta learns which ads bring
demo bookings and paying students.

- **NexaGen** owns the lead record and every automatic fact (demo booked / attended / missed,
  registered, paid, ad click).
- **Frappe** is the sales desk: owner, notes, calls, and the stages a salesperson sets.
- Both show **one pipeline**: the same stage names, and the same stage for each lead.

### Defaults this run takes (owner can change; log each in BACKLOG)

- **Where people change stages:** in either place, and the latest change wins. NexaGen's
  Leads page keeps its stage control (no UI removed).
- **Lead details** (name, phone, child) flow one way, NexaGen → Frappe. Edits in Frappe are
  not copied back.

  are ignored on the way back.

## Phases

Each phase: build → `npm run typecheck` / `lint` for the touched workspaces → unit specs →
integration specs on an `_int` DB where SQL, locks or the webhook are involved → commit.

### Phase 1: Frappe → NexaGen stages (the return path)

- New job (every 15 min, `JobLockService.runExclusive`, new `JOB_LOCKS` entry): for Nexa's
  open leads with a sent `CrmLeadPush` (`externalId` set), read Frappe's stage (batch the
  reads; respect Frappe's rate limits).
- Reverse map from `FRAPPE_LEAD_STAGES`. Unknown names are ignored. "Enrolled" →
  `CONVERTED`.
- Frappe's stage is **a person's change** when it differs from `sentStatus` (the stage NexaGen
  last copied). Apply it like `LeadService.updateStatus` (status-filtered claim, timeline
  activity "Changed in Frappe: X → Y", referral progress as for a manual move). Then set
  `sentStatus` to it so it is never copied back (no loop).
- Never move a `CONVERTED` / `ACTIVE_STUDENT` lead to Lost from Frappe. A Lost lead stops
  getting the "waiting for a demo time" alert, and later automatic moves leave it alone
  (already true via `nextLeadStatus`).
- Switch `FRAPPE_CRM_STAGE_RETURN` (default `false`) in `packages/config`. It needs
  `FRAPPE_CRM_STAGE_SYNC` on as well (same stage names on both sides).
- Specs: the reverse map, no-loop, closed-stage rules, unknown names, claim race (int spec).

### Phase 2: every WhatsApp chat becomes a lead (bot off)

Today, with the bot off, `whatsapp-webhook.service.ts` stores each message and marks it
ignored, and a lead exists only when the bot books a demo. The parser doesn't read the
Click-to-WhatsApp `referral` object at all.

- Parse `messages[].referral` (`source_type`, `source_id` = ad id, `source_url`, `headline`,
  `ctwa_clid`) into the parsed event. Skip coexistence echo fields (`smb_message_echoes`,
  `smb_app_state_sync`) without error.
- **Lead capture** (a new `SupportSettings.captureLeads`, default `false`, env fallback
  `SUPPORT_CAPTURE_LEADS`; shown as a switch on the support settings page). It works while the
  bot is off and sends nothing. On a customer message from a number that is neither an account
  nor an open lead: create a `Lead` with source `WhatsApp ad` (referral present) or
  `WhatsApp`, campaign = ad headline (else ad id), parent name = the WhatsApp profile name.
  Required child fields get clearly named placeholders: one constant, shown as "—" in the
  admin UI, never sent to Frappe as if real. Then `crmPush.enqueue` as the bot's leads do.
  **No migration that makes existing columns nullable.**
- If the number already has an open lead, attach the ad click to it (no new lead).
- New additive table `LeadAdClick` (lead, ad id, `ctwa_clid`, headline, source URL, first
  seen). It keeps the first click and the latest click. Retention: as the lead.
- Specs: parser (referral, echoes), capture rules (account number, open lead, Lost, other
  academy's number), idempotency on the WhatsApp message id; webhook int spec.

### Phase 3: Meta Conversions API (server)

- `meta-capi/` module with a `MetaCapiEvent` outbox (unique per lead + event name; status,
  attempts, next attempt; retention rule). Sent by a sweep job; the enqueue happens in the same
  transaction as the stage change.
- Off unless `META_DATASET_ID` + `META_CAPI_ACCESS_TOKEN` are set (`packages/config`).
  `META_CAPI_TEST_EVENT_CODE` makes every event a test event (for staging later).
- Events from lead stage changes (automatic, manual, or from Frappe):

  | NexaGen | Meta event |
  |---|---|
  | lead created | `LeadSubmitted` (WhatsApp) / `Lead` (website) |
  | Demo booked | `QualifiedLead` (WhatsApp) / `Schedule` (website) |
  | Converted (paid or enrolled) | `Purchase` with value in ₹ when a paid order is linked, else no value |

- **WhatsApp leads** (a `LeadAdClick` exists): `action_source: "business_messaging"`,
  `messaging_channel: "whatsapp"`, `user_data` = WABA id + `ctwa_clid`.
  **Website leads:** `action_source: "website"`, `event_id` shared with the pixel (Phase 4),
  `fbc` from the stored `fbclid`, `fbp` cookie if consented, hashed parent phone/email,
  `client_ip_address` / `user_agent` from the visit.
- **Never** send a child's name, age or account email; only the parent's contact details from
  the lead, hashed (SHA-256, normalised). No event without consent for website leads.
- Specs with a mocked HTTP client: payload shape per source, hashing/normalising, consent
  gating, retry/backoff, other academies skipped.

### Phase 4: Meta Pixel + consent (web)

- `NEXT_PUBLIC_META_PIXEL_ID` (build-time; empty = no pixel and no banner).
- Consent banner (Accept / Decline; choice in a first-party cookie for 6 months) on **Nexa's
  public pages only** (`/`, `/academy`, `/plans`, `/demo` booking, legal pages). Never on
  signed-in pages, live class or any academy's own host (`platform-brand-only`).
- After Accept: load the pixel, `PageView`, `ViewContent` on plans, `Lead` on demo-form submit
  with the same `event_id` the server uses. Save the consent on the visit (`VisitorSession`,
  additive column) so Phase 3 knows.
- CSP: add Meta's script and tracking hosts in `next.config.mjs` `securityHeaders()`.
- `features/legal/content.ts`: replace "the website uses no third-party advertising or
  analytics trackers" with true wording (Meta Pixel after consent, what is sent, how to
  decline). Keep `llms.txt` / JSON-LD consistent.
- UI_RULES apply (tokens, components, focus). Shots on the private stack for the banner at
  all devices; no horizontal overflow.

### Phase 5: Funnel report (admin)

- On the admin Leads area: by source and campaign, over a date range in the academy's zone —
  leads → demo booked → attended → enrolled, with conversion %.
- Optional ad spend: `META_ADS_ACCESS_TOKEN` + `META_AD_ACCOUNT_ID` (read-only Insights,
  cached daily). Empty = no spend columns. Cost per lead / per enrolment when present.
- Server-paged per docs/PAGINATION.md if it lists leads; dates per the Date & Time rule.
