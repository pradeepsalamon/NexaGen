## Calls made in advance (the owner can change these)

1. **The nav reserves only the rail.** From `xl` (1280 px) the page is always
   offset by the collapsed rail width (`4rem`, today's collapsed
   `--app-nav-w`). Expanding the nav slides a `16rem` panel **over** the page.
   The page never moves or resizes. Today both widths shift the page (see
   `AppShell.tsx` and `globals.css` `--app-nav-w`).
2. **The expanded panel behaves like a popover (owner, 2026-11-17).** It keeps
   today's look and the same expand animation, but it floats over the page
   instead of moving it. It closes on its own after navigation. It also closes
   on Escape, the toggle, or a click outside it.
3. **The rail is the resting state.** Every page load and every navigation
   lands on the collapsed rail. On desktop the saved collapse choice
   (`useSidebarStore`) no longer decides what shows. Keep the store key so
   nothing breaks, and log the change.
4. **Rail flyouts open on click, and on hover with intent.** Hover opens after
   ~150 ms and closes after ~250 ms of leaving both the icon and the flyout.
   Click toggles. Keyboard: Enter, Space or ArrowRight opens and focuses the
   first item, and Escape closes and returns focus to the icon. A plain link
   gets a label tooltip, as today. A group gets a flyout that lists its items.
5. **Mobile and tablet stay exactly as they are (owner, 2026-11-17).** Below
   `xl` (1280 px) the current drawer is not changed in any way. The rail and
   the overlay are desktop only.
6. **Field errors are a small message anchored under the field**, and they
   never add height (details in item 2). Native browser bubbles are not used
   for app forms: they look different in every browser, can't be themed, and
   the app already validates with Zod. `noValidate` stays where forms use it.
   Native attributes (`type="email"`, `required`, `min`, `max`, `minLength`,
   `inputMode`, `autoComplete`) are still added for keyboards, autofill and
   screen readers.
7. **Form-level and server errors go to a toast** (`useToast`; `lib/api.ts`
   already shows API errors). Inline red banners inside forms are removed,
   except for one case: a message that must stay on screen while the user acts
   on it (for example a locked account with a wait time) becomes a compact,
   one-line notice of fixed height.

## The work, in order

### 1. App shell: overlay nav with rail flyouts

Branch `feat/app-shell-overlay-nav`, worktree `.worktrees/app-shell`.

**Inspect first:**

- `components/layout/`: `AppShell.tsx`, `Sidebar.tsx` (`NavDrawer`,
  `NavDrawerLink`, `NavDrawerAccordion`, `RailTooltip`), `RoleSidebar.tsx`,
  the four role sidebars, `navItems.ts`, `Header.tsx`, `headerStyles.ts`
- `store/sidebarStore` and the `--app-nav-w` init script in `app/layout.tsx`
- `globals.css` around `--app-nav-w`
- the live-class room, which has its own docked sidebar. Leave the room alone.

**Build:**

- **Fixed offset.** Split the variable into `--app-rail-w` (the fixed page
  offset used by `AppShell` and the pre-paint ground) and the panel's own
  width. The init script sets only what is needed to avoid a flash. The page's
  `xl:pl-…` must never change when the nav is toggled.
- **Overlay panel.** Keep today's expand animation and look, but the panel
  sits above the page (z-index under the header's menus and above page
  content) with `shadow-card`. Only the panel animates; no layout property on
  the page does. Respect `prefers-reduced-motion`. It closes:
  - after any navigation (watch `usePathname`, so a link, back/forward or a
    redirect all count)
  - on Escape (focus goes back to the toggle)
  - on the toggle, or a click or tap outside the panel and header
- **Rail flyouts.** A collapsed `NavDrawerAccordion` becomes a flyout built on
  `components/ui/Popover.tsx` (Radix portal, so the rail's `overflow` can't
  clip it), placed `side="right"` with collision padding. It shows the group
  title plus its links, the active link marked, and badges kept.
  - Selecting an item, clicking outside, or pressing Escape closes it.
  - Moving the pointer from the icon to the flyout doesn't close it (behaviour
    as in call 4).
  - Theme tokens only, `rounded-panel`, and light and dark both checked.
- **Header.** The collapse toggle stays where it is today. No duplicate
  control. The header must not shift when the nav toggles; measure the logo and
  toggle x positions before and after. Search, notifications, the profile menu
  and the theme toggle are untouched.
- **Mobile and tablet: no changes.** Below `xl` the drawer (the `moveDrawer`
  swipe, backdrop, focus handling and looks) must render and behave exactly as
  it does today. Make the desktop changes so they can't reach it: gate them on
  `docked`/`NAV_DOCKED_QUERY` or `xl:` classes. Before and after shots at 390 px
  and 768 px must match. If a regression check finds an existing drawer bug,
  log it in BACKLOG.md; don't fix it in this run.
- **Roles.** Every role's items, badges and feature gates are unchanged. Diff
  the rendered link list per role before and after (super admin, admin, coach,
  student, sales).

**Tests:** add `e2e/app-shell-nav.spec.ts`, using the helpers in
`e2e/fixtures.ts` and the seeded accounts:

1. Desktop at 1440 px: record `main`'s `getBoundingClientRect()` (x, y, width,
   height) and the header toggle's rect. Expand the nav, wait for the
   transition, and record them again. Then collapse and record a third time.
   **All three must be equal.** Repeat at 1280 px.
2. Expanded: clicking a link navigates and closes the panel (back to the rail,
   with `main`'s rect unchanged). Escape and a click outside also close it.
3. Collapsed: hovering a group opens its flyout, and moving into the flyout
   keeps it open. Clicking an item navigates and closes the flyout.
4. Keyboard: Tab to a rail group, press Enter (flyout open, focus on the first
   item), then Escape (closed, focus back on the icon).
5. A click outside closes the flyout.
6. At 390 px (a regression guard only): open the drawer; check that a backdrop
   tap closes it, that a link tap navigates and closes it, and that
   `scrollWidth <= innerWidth`.
7. Each test runs in light and dark (`data-theme`).

**Verify:** typecheck, lint, a worktree web build, the new spec in Chromium
and WebKit against dev.nexachess.in serving this branch, and
`npm run shots -- --path <route> --devices all --theme both` for
`/admin/dashboard`, `/coach/dashboard` and `/student/dashboard`, with nav
expanded and collapsed and 0 horizontal overflow. Look at the screenshots, not
only the overflow numbers. Update [UI_RULES.md](UI_RULES.md) (the nav section)
and [RESPONSIVE.md](RESPONSIVE.md) with the fixed-rail rule.

### 2. Form validation: shared behaviour

Branch `fix/form-validation-ux`, worktree `.worktrees/forms`. Do this before
item 3: it's the foundation that item 3 rolls out.

**Inspect first:**

- `components/ui/FormField.tsx` (today the error is a `<p>` under the input,
  which adds height)
- `Input.tsx`, `PasswordInput.tsx`, `fieldStyles.ts`
- `hooks/useTouchedFields.ts`
- `lib/errors.ts` `getErrorMessage`, `lib/api.ts` error toasts
- `features/auth/components/LoginForm.tsx` (the owner's example: submitting an
  empty email)
- the react-hook-form forms (`grep -rlE 'useForm[<(]'`, about 17 files)

**Build** (with no new form library and no second validation system):

- **`FormField` reserves no space and shifts nothing.** The error renders as a
  small message absolutely positioned just under the input, inside the field's
  existing bottom gap, above the next field. It uses a danger icon and text,
  and wraps to two lines at most, so meaning never rests on colour alone.
  Then:
  - the input gets `aria-invalid` and `aria-describedby` pointing at the
    message
  - the message keeps `role="alert"` only when it first appears after a submit,
    so screen readers don't announce on every keystroke
  - the hint keeps today's static slot
  - confirm that no message overlaps the next field's label at the tightest
    field gap used. If one would, raise that form's gap (fixed, not
    error-dependent).
- **A helper for forms that don't use `FormField`**, for example
  `components/ui/FieldError.tsx` with the same visuals, or `FormField`
  extended. One component, not two.
- **Timing.** An error shows after blur (touched) or on submit, never on load.
  It clears as soon as the value becomes valid. Submit focuses the first
  invalid field. `useTouchedFields` already does most of this; reuse it, and
  for react-hook-form use `mode: "onTouched"`.
- **Messages.** They are short and human ("Enter your email", "Enter a valid
  email", "Use at least 8 characters"). Never show raw Zod or server text.
  Check `getErrorMessage` for paths that can surface stack or technical text.
- **Login first.** Apply all of this to `LoginForm`, register, forgot password,
  reset password and the MFA step, and prove it on the owner's example.

### 3. Form validation: the audit and the sweep

Same branch as item 2, one commit per area so the PR reads in steps.

**Audit.** Build the inventory before changing anything: every `<form`, every
`useForm`, every dialog or sheet with inputs (about 42 + 17 files, and about 49
dialogs with inputs), and inline save buttons outside a `<form>`. Write it to
`docs/FORM_VALIDATION_AUDIT.md`, one table row per form:

- route or dialog
- file
- validation used today
- how errors show today
- what changed
- tested: auto, manual, or not tested

Group the rows by area:

- auth and account (profile, password, email change, MFA)
- people (student, coach, admin, sales; invites)
- batches, classes and schedules (including cancellation and approval requests)
- live-class pre-class settings and in-room dialogs
- assignments, homework, puzzles and puzzle sets, MCQ and Playout, courses and
  activities
- tournaments
- payments, discounts, invoices and payroll
- messaging, email, announcements, the knowledge base and support settings
- branding, legal pages and platform / SaaS console forms
- leads, demo classes and referrals
- search and filter forms (only where they validate)
- feedback forms and settings pages

**Sweep, for each form:**

- Replace any inline error rendering that adds height, and any red banner
  block, with item 2's field message or a toast (call 7).
- Add the native attributes from call 6 where they are missing.
- Number, date and time fields: the client schema must respect the same limits
  the API enforces. Read the matching Zod schema in `@nexa-chess/types`, or the
  DTO. **Don't loosen or invent a rule**; if the client and server disagree,
  log it in BACKLOG.md.
- A field with no field message (a missing select, a radio group) gets the
  same message under its group.
- Dialogs: an error must not grow the dialog or make it scroll where it didn't
  before. Check at 390 px.
- Keep every `onSubmit`, mutation, invalidation and undo exactly as it is.

**Tests:** add `e2e/form-validation.spec.ts` covering one representative form
per area. Each test checks:

- the empty submit is blocked (no network request: watch with
  `page.waitForRequest` plus a timeout, or route counting)
- the message text is visible and has `aria-describedby`
- the form's and dialog's `getBoundingClientRect()` height is unchanged
  before and after the error
- correcting the input clears the error and the submit succeeds
- a server error (for example a duplicate email on create-student, or a wrong
  password) shows a toast with a human message and no layout change

Cover:

- login: empty email, invalid email, wrong password (server)
- register or reset password: password rules
- create student in a dialog: required fields and duplicate email (server)
- a batch or class form: a number limit and an invalid date or time
- a select field left empty
- editing an existing record: the record loads, an edit is saved, and a bad
  edit is blocked
- the same login and dialog checks at 390 px, and in dark theme

**Be honest about coverage.** The audit table's "tested" column must say which
forms were only read, which were clicked through by hand, and which have an
automated test. Do not claim every form was tested.

**Verify:** typecheck, lint, a worktree web build, the new spec in Chromium,
and `npm run shots` on the login page plus three dialog-heavy pages (both
themes, all devices) with an error showing. To show the error state, a
small `--action` hook in the shots script is fine if one doesn't exist; check
[scripts/responsive/README.md](../scripts/responsive/README.md) first.
Update [UI_RULES.md](UI_RULES.md) with the form-error rule (one paragraph,
naming the component) and add a pre-PR checklist line.
